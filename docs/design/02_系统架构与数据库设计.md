# 生鲜冷链物流协同优化系统 架构与数据库设计

## 1. 推荐技术架构

### 1.1 总体架构

```text
浏览器后台 / 司机移动端
        |
        | HTTPS
        v
Nginx 反向代理
        |
        v
FastAPI 后端服务
        |
        |---------------- PostgreSQL + PostGIS
        |---------------- Redis
        |---------------- OR-Tools 优化 Worker
        |---------------- 对象存储 OSS/COS/S3
        |---------------- 高德地图 API
```

### 1.2 前端

后台端：

- Vue 3
- TypeScript
- Element Plus
- Pinia
- Vue Router
- ECharts
- Three.js
- 高德地图 JS API

司机端：

- Vue 3
- TypeScript
- Vant
- 响应式 H5
- 调用手机地图导航

### 1.3 后端

推荐：

- Python FastAPI
- SQLAlchemy
- Alembic
- Pydantic
- OR-Tools
- Celery 或 RQ
- Redis
- PostgreSQL + PostGIS

为什么推荐 FastAPI：

- Python 生态适合 OR-Tools、优化算法、数据处理。
- FastAPI 接口开发效率高。
- Pydantic 适合做订单导入校验。
- 后续接机器学习货损模型更方便。

### 1.4 部署

推荐 Docker Compose 起步：

- `web-admin`：后台前端
- `web-driver`：司机端前端
- `api`：FastAPI
- `worker`：优化任务 Worker
- `postgres`：数据库
- `redis`：队列与缓存
- `nginx`：HTTPS 与静态资源代理

生产环境：

- 云服务器 2-4 核起步
- PostgreSQL 独立磁盘
- 自动数据库备份
- HTTPS 证书
- 日志轮转

## 5. OR-Tools VRPTW 求解设计

### 5.1 输入

```json
{
  "depot": {},
  "orders": [],
  "vehicles": [],
  "distance_matrix": [],
  "time_matrix": [],
  "capacity_demands": [],
  "volume_demands": [],
  "time_windows": [],
  "service_times": []
}
```

### 5.2 约束

- 每个订单必须被服务一次。
- 每辆车从配送中心出发并返回配送中心。
- 每辆车载重不得超过额定载重。
- 每辆车体积不得超过货厢容积。
- 每辆车箱数不得超过装箱容量。
- 到达时间必须满足客户时间窗。

### 5.3 目标函数

第一阶段：

```text
严格满足所有时间窗，最小化综合成本。
```

若无可行解：

第二阶段：

```text
允许迟到，最小化总迟到分钟数。
```

同时保存：

```text
允许迟到条件下的最低成本方案。
```

### 5.4 输出

```json
{
  "solutions": [
    {
      "type": "on_time_min_cost",
      "routes": [],
      "total_cost": 0,
      "on_time_rate": 1,
      "total_tardiness_min": 0
    }
  ]
}
```
